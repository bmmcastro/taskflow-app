TaskFlow — Relatório Técnico

UC00609 — Desenvolver aplicações móveis (plataforma Android) · Trabalho individual
Autor: Bruno Castro · Código: github.com/bmmcastro/taskflow-app

1. Introdução

Na UC00605 (Programar para a web, vertente servidor) a nossa equipa desenvolveu o TaskFlow: uma aplicação web de gestão de tarefas em equipa (Node.js + Express + PostgreSQL), publicada em https://taskflow.algarit.pt. Para esta UC decidi levar esse projeto para Android nativo em Kotlin: a app é um cliente da mesma API — mesma conta, mesmos dados, outra plataforma. O que muda num lado aparece no outro.

3. Arquitetura

Single-activity com Navigation (Jetpack) e MVVM:

app/src/main/java/com/algarit/taskflow/
├── MainActivity.kt   a única activity: Toolbar + NavHostFragment
├── ConviteActivity   entrada de quem recebe convite (fora do grafo)
├── api/      ApiService (interface Retrofit) + Api (cliente, erros) + Sessao
├── model/    data classes Gson + enum EstadoTarefa
├── data/     Repo — coroutines (paralelismo do quadro)
├── ui/       um Fragment + um ViewModel por ecrã (9); UiState (sealed class); Ui (ajudas)
└── adapter/  5 ListAdapter + DiffUtil
  • Grafo de navegação com 8 destinos e ações; ids por Safe Args (erro de compilação em vez de runtime).
  • Toolbar ligada ao NavController: o botão Voltar aparece nos ecrãs secundários.
  • UiState (Idle / Loading / Sucesso / Erro), uma sealed class observada por LiveData; o Idle existe para os formulários — começar em Sucesso fazia navegar sozinho ao observar o valor inicial (bug detetado na revisão do formador).

4. Ligação à API

Retrofit + Gson: interface com todos os endpoints como funções suspend; cliente único com timeouts (15 s / 30 s). Os ViewModels chamam-nas dentro de viewModelScope.launch — sem callbacks, cancelamento automático com o ecrã. Comecei com Volley e migrei para Retrofit + coroutines quando chegámos à matéria: o código dos ecrãs ficou sequencial e desapareceram os guardas de ciclo de vida.

Autenticação igual à do site (id do utilizador nos pedidos), guardada em SharedPreferences. Endpoints usados:

ÁreaEndpoints
Login / Registo / PerfilPOST /utilizadores/login · POST /utilizadores/registo · PATCH /utilizadores/:id
ProjetosGET, POST, DELETE /projetos
TarefasGET, POST, PATCH, DELETE /tarefas · GET /tarefas/relatorio
SubtarefasGET, POST, PATCH, DELETE /subtarefas
Membros / ConvitesGET, POST /projetos/:id/membros · DELETE /projetos/:id/membros/:uid · POST /projetos/:id/convidar · GET /projetos/:id/convites · GET /convites/:token · POST /convites/:token/aceitar

5. Threads e coroutines (Sessão 11)

  • Nada bloqueia a main thread: nunca Thread.sleep, runBlocking ou GlobalScope.
  • O quadro carrega membros e tarefas em paralelo (async/await) dentro de withContext(Dispatchers.IO) no Repo; os membros e convites do ecrã Membros também.
  • Cancelamento: o ViewModel guarda o Job e cancela o anterior ao recarregar.
  • Erros distintos: sem ligação / timeout / resposta inválida / servidor (erroAmigavel). A ordem dos ramos conta: a exceção de JSON mal formado também é um IOException, por isso é tratada antes do ramo da falta de ligação.
  • ProgressBar em todos os ecrãs com pedidos (login, registo, projetos, quadro, detalhe, membros, relatório, perfil e convite), ligada ao estado Loading; nos projetos e no quadro há também o puxar para atualizar.

6. Interface e recursos

  • Views em XML com ConstraintLayout em todos os ecrãs, diálogos e itens de lista (cadeias verticais nos formulários, cadeias horizontais nos blocos do relatório); ViewBinding em todos os ecrãs e diálogos, sem findViewById; cinco listas com ListAdapter + DiffUtil.
  • Elementos nativos variados: EditText com validação (setError), Switch para esconder concluídas, Spinner para a coluna da tarefa, ImageView, Toast e Snackbar com ação.
  • Textos, cores, dimensões e temas em recursos (strings.xml, colors.xml, dimens.xml, themes.xml); modo noturno (values-night).
  • Design próprio: cartões, separadores com contagens, chips de filtro, slogans por ecrã; prazo atrasado a vermelho.
  • Acessibilidade: contentDescription nos botões de imagem.

7. Qualidade e testes

  • 10 testes unitários (JUnit) — formatação de datas, mapeamento JSON→modelos pelo Gson (incluindo campos que vêm a null) e a conversão do texto da API para o enum do estado — todos a passar.
  • 2 testes instrumentados (androidTest): tocar na checkbox de uma subtarefa dispara a ação do adapter e uma linha reutilizada mostra o estado certo.
  • Build release assinada com keystore própria (RSA 2048); senhas no local.properties, fora do git.
  • Verificada ecrã a ecrã no emulador (API 35), com as capturas no manual.
  • Revisão do formador aplicada: ciclo login-projetos (UiState.Idle), convite sem sessão, setas duplicadas, enum do estado, mensagens de erro distintas, setError nas validações, dimens.xml, ConstraintLayout, senhas fora do build.

8. Dificuldades encontradas

  • Toolchain do Java (em dois tempos). Primeiro um jlink inexistente: o Gradle detetou um JRE de extensão do VSCode sem JDK. Resolvi fixando o JDK no gradle.properties — e semanas depois o fix morreu (o Adoptium atualizou, o caminho desapareceu). Lição: caminhos absolutos de JDK em projetos partilhados são armadilha; o Gradle JDK do IDE resolve.
  • Gson e valores por omissão. Tarefa sem status no JSON ficava null: o Gson, sem construtor sem argumentos, marca todos os campos. Correção: defaults em todos os parâmetros da data class.
  • UTF-8 na linha de comandos. Ao registar dados por curl, acentos chegavam corrompidos (code page ANSI do Windows). Correção: JSON em ficheiro UTF-8 com --data-binary.
  • Safe Args + AGP 9. A versão 2.9.x recusa-se a aplicar; subi para 2.10.2.
  • PATCH das tarefas. A API exige título, responsável e prazo em todos os PATCH — mover uma tarefa reenvia-a completa com o estado novo.
  • Um campo que vem a null. No detalhe de certas tarefas ficava um espaço vazio onde devia estar o link: a API devolve "link": null quando a tarefa não tem link, mas o modelo declarava link como String não anulável. O Gson põe null na mesma e o teste isNotBlank dizia que havia link. Correção: link: String? no modelo, tratado com isNullOrBlank e orEmpty, e um teste unitário a fixar o caso.
  • ConstraintLayout dentro de ScrollView. Ao converter os ecrãs, prender o último elemento ao fundo do contentor fazia-o descer até ao fim do ecrã (o ScrollView estica o contentor). Correção: sem restrição ao fundo nos ecrãs com rolagem — o conteúdo fica no topo e o espaço livre fica em baixo.
  • Teste instrumentado depois de mudar um layout. O teste falhou com NoSuchMethodError porque o código de teste estava compilado contra a classe de binding antiga (raiz LinearLayout). Não era da app: bastou limpar os ficheiros gerados do androidTest e recompilar.

9. Como testar

  1. Abrir o projeto no Android Studio e fazer Run (Android 7.0+).
  2. Conta de demonstração: demo@taskflow.pt / 1234 (mesma base de dados do site).
  3. Criar uma tarefa na app e vê-la no site — e vice-versa.

10. Conclusão

Ficou feita a app Android do TaskFlow, ligada à API do projeto da UC00605, com as funções principais completas. Pelo caminho foi reescrita por razões certas: para a arquitetura single-activity com Navigation e Safe Args, de Volley para Retrofit com coroutines e MVVM, recebeu a matéria da sessão 11 (paralelismo, dispatchers, cancelamento), uma revisão completa do formador e, no fim, um redesenho visual com modo noturno e um teste instrumentado. Para além do resultado, deu-me prática real em consumir uma API REST em Android, em evoluir uma app sem a partir, e a resolver problemas de ferramentas que fazem parte do dia a dia.

Melhorias futuras: arrastar cartões entre colunas, notificações de prazos, envio de convites por email, sincronização offline.
